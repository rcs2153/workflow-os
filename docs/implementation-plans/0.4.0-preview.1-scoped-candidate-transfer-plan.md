# 0.4.0-preview.1 Scoped Candidate Transfer Plan

Status: corrected after focused review; no workflow dispatch or external
mutation is authorized

## 1. Decision

Do **not** use a GitHub draft release as candidate staging. Add a manually
dispatched native macOS arm64 candidate workflow beside the accepted Linux
x86-64 musl workflow, merge both workflow definitions and their contract tests,
then rebuild both candidates from that one exact post-merge commit. Each
workflow uploads one immutable seven-day GitHub Actions artifact.

The accepted earlier candidates remain truthful production evidence, but they
are not the final transferable pair because only Linux received bounded hosted
storage. Rebuilding both targets from the later exact workflow-definition
commit produces one coherent, reviewable transfer boundary and avoids creating
a future release object before publication is authorized.

GitHub currently provides native arm64 macOS hosted runners for public
repositories under `macos-15`, and Actions artifacts support per-artifact
retention. These platform contracts make a draft-release staging object both
unnecessary and less safe.

Official platform contracts:

- [GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)
- [Store and share data with workflow artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data)
- [Removing workflow artifacts](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts)

## 2. Provenance Reset

The new candidate source is not known until the workflow implementation PR is
squash-merged. Call that exact merge commit `CANDIDATE_SOURCE`.

Both hosted candidate workflows must:

- exist at `CANDIDATE_SOURCE`;
- accept only one exact 40-character `source_commit` input;
- reject unless `source_commit == github.sha` for the reviewed workflow
  definition;
- check out exactly `CANDIDATE_SOURCE` in detached state;
- reject a dirty tree or version drift;
- build and execute the native target binary;
- package only with explicit `--final-candidate` posture;
- verify manifest, checksum, source, target, version, install, overwrite
  refusal, uninstall, and state preservation;
- emit one payload-minimal candidate evidence record; and
- upload exactly the archive, checksum, and evidence record with seven-day
  retention.

The preceding candidate source
`33a77cb27fb989cb4e1695788df5eee591695aa6` and its artifacts become
`superseded_by_transfer_reset` after both new runs pass. They remain historical
evidence and must not be relabeled, deleted by implication, or cited as the
publishable pair.

## 3. macOS Workflow Contract

Add `.github/workflows/final-candidate-macos.yml` with:

- `workflow_dispatch` only;
- `contents: read` and no write permission;
- concurrency keyed by exact source commit;
- `runs-on: macos-15`;
- a pinned checkout action revision;
- the repository's pinned Rust toolchain;
- explicit `uname -m == arm64` admission;
- native target `aarch64-apple-darwin`;
- exact source/workflow-definition equality;
- no credentials, secrets, signing, notarization, package manager, release,
  tag, or registry step; and
- `actions/upload-artifact` pinned to the accepted immutable revision with
  `retention-days: 7`.

The workflow must execute the built CLI and observe exactly
`workflow-os 0.4.0-preview.1`. Cross-compilation or binary-shape inspection
alone is insufficient for native admission.

The uploaded artifact name must be:

`workflow-os-v0.4.0-preview.1-macos-CANDIDATE_SOURCE`

The archive inside it must remain:

`workflow-os-v0.4.0-preview.1-aarch64-apple-darwin.tar.gz`

## 4. Linux Workflow Reuse

Reuse `.github/workflows/final-candidate-linux.yml` without broadening its
permissions or outputs. Dispatch it again only after the macOS workflow and its
tests are merged. Its `source_commit` must equal the same `CANDIDATE_SOURCE`.

The uploaded artifact name must be:

`workflow-os-v0.4.0-preview.1-linux-CANDIDATE_SOURCE`

The archive inside it remains:

`workflow-os-v0.4.0-preview.1-x86_64-unknown-linux-musl.tar.gz`

If review identifies a contract mismatch between the two workflows, correct
the shared contract before dispatch rather than changing only one target's
evidence semantics.

## 5. Closed External Transition Set

One later proof-backed `dg/release` approval may enumerate only:

1. dispatch the macOS workflow at exact `CANDIDATE_SOURCE` once;
2. dispatch the Linux workflow at exact `CANDIDATE_SOURCE` once;
3. inspect both exact workflow runs;
4. download both exact workflow artifacts for verification; and
5. reread artifact metadata and expiry.

The approval must not imply or authorize:

- creating, editing, publishing, or deleting a GitHub Release;
- creating, moving, or deleting a Git tag;
- rerunning failed jobs or blindly redispatching an ambiguous workflow;
- changing artifact retention or repository Actions settings;
- deleting workflow runs or artifacts;
- Rust or npm registry publication;
- signing, notarization, package-manager distribution, announcement, or Hacker
  News submission; or
- any provider mutation not listed above.

The live GitHub connector is not yet a Workflow OS-enforced external-action
capability consumer. Workflow dispatch and artifact retrieval therefore remain
disclosed out-of-kernel executor work under the proof-backed phase approval;
this plan does not claim live delegated-authority projection.

## 6. Dispatch And Ambiguity Rules

Before each dispatch, prove:

- `CANDIDATE_SOURCE` is the exact merged workflow-definition commit;
- all required CI checks on that commit are terminal green;
- no prior candidate run exists for the same workflow and exact source; and
- the release state still identifies publication as unauthorized.

After dispatch, bind the returned workflow run ID to repository, workflow file,
event, source commit, attempt, and actor. If the dispatch response is ambiguous,
query runs by workflow and exact head before considering another request. Exact
found reconciles success; exact absent permits one dispatch only when the
provider establishes that no run was created; inconclusive state remains a
resumable wait. Do not create duplicate candidate runs to make progress look
cleaner.

Failure of either target blocks the pair. A corrected source or workflow change
creates a new `CANDIDATE_SOURCE` and requires both targets to rebuild.

## 7. Artifact Admission

For each terminal-success run, record and verify:

- workflow definition path and commit;
- run ID, attempt, actor, creation time, and terminal conclusion;
- artifact ID, exact name, byte size, creation time, expiry, and retention;
- archive and binary SHA-256;
- native target and binary shape;
- manifest schema, package posture, source commit, and dirty-tree posture;
- native version execution;
- install, overwrite refusal, uninstall, and state-preservation results; and
- the absence of tag, release, registry, and announcement mutations.

Download each artifact by exact ID and verify its archive checksum against the
workflow evidence record. Missing, expired, duplicate, renamed, unexpected, or
checksum-mismatched artifacts block admission. Do not rebuild locally to fill a
hosted-evidence gap.

GitHub Actions artifacts expire automatically. Their seven-day lifetime is a
review window, not permanent distribution. A later publication decision must
either consume the exact admitted bytes before expiry or require a separately
reviewed full-pair rebuild from a new exact commit.

## 8. Durable Release Evidence

After both artifacts pass, update the release state and candidate report with:

- new exact `candidate_source_commit`;
- both workflow-definition commits;
- both run and artifact IDs;
- exact artifact names and expiry timestamps;
- archive and binary digests;
- `storage_posture: bounded_actions_artifact`;
- `retention_days: 7`;
- supersession links to the earlier candidate pair; and
- `publication_authorized: false`.

Release-state validation must reject mixed source commits, missing workflow
identity, nonterminal runs, target duplication, digest drift, expired artifacts,
or any publication authority. The checklist transfer gate may close only after
the machine-readable state, human report, and downloaded artifact verification
agree.

The evidence commit occurs after candidate production and is an audit record;
it is not the candidate source. Any code, workflow, manifest, lockfile,
`README.md`, or `LICENSE` change after `CANDIDATE_SOURCE` invalidates both
candidates. Post-candidate evidence reports may advance without changing the
candidate bytes, but the later publication decision must explicitly distinguish
those audit commits from the tagged candidate source.

## 9. Frozen Validation And Independent Assurance

After transfer evidence is persisted:

1. rerun the complete frozen validation matrix from an isolated checkout of
   `CANDIDATE_SOURCE`;
2. run install and uninstall checks from both downloaded hosted artifacts;
3. preserve opt-in live-test classification without fabricating execution;
4. obtain independent release/security assurance against the exact candidate
   pair and current product contract; and
5. only then start a separate publication decision.

The external evaluator's current-main product review is valuable acceptance
evidence but explicitly reports that independent release/security assurance is
still missing. This plan does not relabel that review.

## 10. Implementation Sequence

1. Focused maintainer/security review of this corrected plan.
2. Implement the macOS workflow and symmetric contract tests.
3. Focused review of workflow permissions, exact-source admission, native
   execution, package verification, artifact contents, and retention.
4. Merge only a terminal-green unchanged workflow head.
5. Start a new proof-backed `dg/release` phase enumerating both dispatches and
   artifact reads.
6. Dispatch both workflows at the exact merge commit.
7. Verify both terminal runs and downloaded artifacts.
8. Persist and review the superseding candidate evidence.
9. Rerun exact-source frozen validation.
10. Obtain independent assurance and return for publication review.

## 11. Acceptance Criteria

- both workflow definitions exist at one exact terminal-green commit;
- macOS runs natively on arm64 and Linux runs natively on x86-64 musl;
- both final-candidate packages derive from that same exact commit;
- exactly one bounded Actions artifact exists for each target;
- artifact contents, names, checksums, manifests, and native version execution
  pass the accepted contract;
- both artifacts expire after seven days and no retention setting is widened;
- the earlier candidate pair is preserved as superseded evidence;
- no draft or published release and no `v0.4.0-preview.1` tag exists;
- the transfer gate closes without closing independent assurance or publication
  gates; and
- reports distinguish kernel governance from out-of-kernel GitHub dispatch and
  download operations.

## 12. Non-Goals

This plan does not implement a live GitHub connector in Workflow OS, weaken the
delegated-authority projection roadmap, create a package registry, add signing
or notarization, claim independent assurance, publish a release, create a tag,
or announce availability.
