## 1. Purpose

Prepare Workflow OS `0.4.0-preview.1` as the next honest public-preview
identity and add a fail-closed final native-archive candidate path without
publishing a tag, release, package, asset, or announcement.

This plan follows the [Phase 5 publication identity
decision](../concepts/HACKER_NEWS_LAUNCH_ADMISSION_PHASE_5_PUBLICATION_IDENTITY_DECISION.md)
and its [focused
review](../concepts/HACKER_NEWS_LAUNCH_ADMISSION_PHASE_5_PUBLICATION_IDENTITY_REVIEW.md).
The existing `v0.3.0-preview.1` tag and GitHub Release remain immutable
historical evidence.

## 2. Governing Invariants

1. One public release identity resolves to one immutable source history.
2. Rust crates, npm packages, CLI output, provider identity, release records,
   archives, manifests, and checksums must agree on the exact version.
3. Final-candidate packaging is an explicit posture, never a missing
   `--provisional` flag or a caller-selected boolean default.
4. A final candidate must come from an exact clean checkout and a native binary
   whose target and version are executed and verified.
5. Packaging authority does not imply upload, tag, registry, GitHub Release,
   or announcement authority.
6. Candidate artifacts are evidence for a later publication decision, not
   evidence that publication occurred.
7. Historical `0.1`, `0.2`, and `0.3` release records are not rewritten into
   current-version documents.
8. Unsupported platform, dirty checkout, mismatched source, mismatched
   version, mismatched target, missing posture, ambiguous posture, failed
   checksum, failed install, or failed uninstall must stop before a candidate
   can be admitted.

## 5. Final Packaging Contract

### 5.1 Explicit Posture

Replace the exported packager's defaulted `provisional` boolean with an
explicit closed posture type containing exactly:

- `provisional_rehearsal`; and
- `final_candidate`.

The CLI must require exactly one explicit posture flag. The proposed interface
is:

```text
--provisional
--final-candidate
```

Missing both or passing both fails before reading the binary or writing the
output directory. Internal callers and tests must also provide posture
explicitly.

### 5.2 Final Candidate Admission

`final_candidate` must require all of the following:

- exact 40-character source commit;
- checkout `HEAD` equals the requested source commit;
- repository tracked and untracked status is clean;
- target is one of the two selected native targets;
- current host platform and architecture match the target contract;
- `file` identifies the expected native binary shape;
- executing the binary returns exactly `workflow-os 0.4.0-preview.1`;
- every Rust and npm package version agrees;
- the archive manifest identifies final-candidate posture;
- archive and checksum output paths do not already exist; and
- deterministic archive generation succeeds without weakening install,
  overwrite-refusal, uninstall, or state-preservation behavior.

Final-candidate posture must categorically reject disabled native or repository
verification through every exported API, not only the executable CLI. Focused
tests must create a real temporary Git repository, clean exact commit, package
manifests, and executable fixture or test a lower-level non-admitting archive
builder that cannot emit final-candidate posture. A caller-selected test option
must never mint a final manifest.

### 5.3 Manifest Evolution

Promote the unpublished provisional package manifest to
`workflowos.dev/release-package/v1` with an explicit `posture` field. Preserve
the exact version, target, source commit, clean-checkout fact, binary SHA-256,
install contract, and state posture.

The manifest must not contain credentials, environment values, raw Git status,
host paths, repository remotes, user identity, or mutable branch names.

### 5.4 Output Safety

The packager must calculate and validate all admission facts before creating
the output directory. It must refuse to overwrite an archive, checksum, or
candidate root with the same name. A failed candidate attempt must not leave a
partial archive presented as complete.

Temporary-file and atomic-rename handling should be used where practical. If
the platform cannot provide the required atomic boundary, the packager must
clean up its own temporary output and report the limitation without deleting
pre-existing user files.

## 6. Required Tests

Focused package tests must prove:

- explicit provisional rehearsal still produces deterministic output;
- explicit final candidate produces deterministic output from an admitted
  fixture;
- missing and conflicting posture fail before output;
- dirty checkout fails final-candidate admission;
- source/HEAD mismatch fails;
- package-version mismatch fails;
- binary-version mismatch fails;
- host/target mismatch and unsupported target fail;
- archive/checksum overwrite fails;
- final manifest uses v1 and records `final_candidate` plus a clean checkout;
- provisional manifest cannot be mistaken for final;
- checksum verification passes;
- install works in an isolated destination;
- install refuses overwrite without `--force`;
- invalid installer arguments fail;
- uninstall is idempotent and preserves `.workflow-os` state; and
- a failed final-candidate attempt leaves no admitted partial output.

Release-identity tests or checks must prove every active package and provider
identity agrees with the selected version. CLI text and JSON version tests must
continue to derive expectations from the built package version rather than a
second literal.

## 7. Native Candidate Evidence

Final candidates must be built only after the implementation PR is merged and
from one exact clean commit.

That commit becomes frozen candidate input. Any source, documentation,
manifest, lockfile, workflow, or release-note change invalidates both native
artifacts and requires rebuilding them from the new exact commit. A later
publication decision may consume candidate evidence without changing the
candidate source. Any decision record intended to ship in the release must
already exist in the frozen commit; post-decision audit records belong to a
subsequent commit.

### 7.1 Apple Silicon macOS

On a matching native host:

1. create or verify a clean checkout of the exact candidate commit;
2. build `workflow-os` in release mode;
3. run focused and release validation;
4. invoke explicit final-candidate packaging;
5. verify checksum, manifest, binary version, install, overwrite refusal,
   uninstall, and state preservation; and
6. record artifact name, SHA-256, source commit, target, and validation refs in
   the governed release report.

### 7.2 Linux x86-64 musl

Use a matching native Linux x86-64 environment bound to the same exact commit.
The workflow must run the same candidate admission and behavioral checks. If a
GitHub Actions artifact is used to transfer the candidate for review, that
upload is a separately authorized, finite-retention candidate-storage action,
not a GitHub Release publication. Its run ID, artifact ID, checksum, retention,
and source commit must be recorded.

Do not claim a final two-platform candidate if either native target lacks an
inspectable artifact and checksum from the same exact source commit.

## 8. CI And Workflow Boundaries

Keep ordinary pull-request CI credential-free and provisional. It should test
the packaging contract and build a rehearsal archive, but must not emit or
upload a final candidate.

Any candidate-production workflow must be separately reviewed and manually
dispatched with an exact immutable commit, least-privilege read permissions,
no tag or release mutation permission, and explicit artifact-retention bounds.
It must reject branch-only input, dirty or mismatched source, and version drift.
The workflow definition and every third-party action must be bound to reviewed
immutable revisions; mutable action tags are insufficient for candidate
production. Evidence must record the workflow-definition commit separately
when it differs from the candidate source commit.

Candidate-storage upload requires a scoped external-action authorization and
must bind repository, workflow run, exact source commit, artifact names,
checksums, retention, and permitted upload count. It cannot inherit GitHub
Release or package-registry mutation authority.

The candidate workflow is evidence production. A later `dg/release` phase must
inspect that evidence before any external release mutation is authorized.

## 9. Implementation Sequence

### Phase A: Focused Plan Review

Review version selection, active/historical classification, final-package
admission, manifest evolution, artifact transfer, and publication separation.
Correct all P0/P1 findings before code work.

### Phase B: Version Identity Alignment

Update machine-readable identities, active docs, changelog, and new `0.4`
release records. Replace the manually synchronized GitHub sandbox user agent
with a compile-time version-derived value. Regenerate lockfiles using the
repository toolchain. Do not change runtime semantics.

### Phase C: Final Packaging Implementation

Implement explicit posture, final admission, v1 manifest, no-overwrite output,
and focused tests. Update the archive contract and release process. Keep the PR
CI job provisional.

### Phase D: Focused Release And Security Review

Run the complete local release matrix, dependency audits, focused packaging
tests, version checks, documentation checks, and diff checks. Review output
handling, exact-commit binding, manifest disclosure, install/uninstall safety,
and historical release preservation.

### Phase E: Merge And Exact-Commit Candidate Production

Merge only a terminal-green unchanged head. Build both native candidates from
the exact resulting commit under a new governed release phase. Preserve
artifacts and checksums as bounded evidence; do not publish them as release
assets.

### Phase F: Separate Publication Decision

Only after candidate artifacts and exact-head evidence exist, start a new
governed publication phase. Its approval handoff must enumerate each intended
external transition separately: tag creation, GitHub Release creation, each
asset upload, optional registry publication, and announcement. Unlisted actions
remain denied.

## 10. Acceptance Criteria

- all active version surfaces report `0.4.0-preview.1`;
- historical release records still identify their original versions and
  commits;
- current docs and changelog accurately distinguish `0.3` from `0.4`;
- package APIs and CLI require explicit posture;
- provisional output cannot be promoted or mislabeled as final;
- final-candidate admission fails closed for every listed mismatch;
- v1 manifest and checksum are deterministic and payload-minimal;
- ordinary PR CI remains non-publishing;
- both native candidate artifacts derive from one exact clean reviewed commit;
- install and uninstall contracts pass for both targets;
- candidate storage, if used, is disclosed and bounded;
- candidate source remains frozen after both native artifacts are admitted;
- no tag, release asset, registry package, or announcement exists before the
  separate publication decision; and
- focused review records the continuing distinction between owner-conducted
  review and independent external security assurance.

## 11. Strict Non-Goals

This plan does not authorize:

- moving, deleting, or replacing an existing tag or release;
- attaching later-commit artifacts to `v0.3.0-preview.1`;
- publishing a tag, GitHub Release, crate, npm package, or announcement;
- Windows, Intel macOS, Linux arm64, package-manager, container, signing, or
  notarization support;
- production readiness, v1 stability, or enterprise support claims;
- reproducible-build, signed-binary, notarization, or authenticated-checksum
  claims; deterministic packaging covers identical binary inputs only;
- broad provider mutation, arbitrary command execution, hosted expansion,
  nested harness work, or another runtime primitive family; or
- bypassing a failed check or using a dirty candidate archive.
