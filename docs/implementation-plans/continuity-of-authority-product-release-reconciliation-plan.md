## 3. Drift Findings

### Current Product Contract

The current contract correctly describes the three individual gate closures in
its detailed sections but still says the cross-gate review is pending. It also
lists absence of proof for the three gate invariants as current non-capabilities.
Those statements are stale after PR #746.

The correction must say:

- the three gates and private cross-gate model are accepted for their exact
  paths;
- production replacement execution and broad continuity claims remain
  unavailable;
- unsupported provider families and writes do not inherit Gate 3; and
- gate closure is necessary but not sufficient for release or v1.

### WorkReport Replay

The roadmap still names a future body-commitment replay-enforcement phase.
Gate 2 already traced and tested supported terminal/provider replay consumers,
including PostgreSQL transaction-local reads, CLI inspect/replay rejection,
recovery, and duplicate reconciliation. The stale phase must close as absorbed
by Gate 2 rather than creating a duplicate implementation lane.

This does not weaken the remaining storage-owner trust limitation. A privileged
owner who can rewrite both a report and every local anchor remains inside the
current trust boundary.

### Validator Assurance

The local-check assurance model and closed trusted-host project-validation
composition truthfully classify the current result as operator-selected,
content-bound, host-observed, unattested, and externally unverifiable. The
projection is currently returned only through the bounded in-process route.

The evidence-integrity P0 remains open until the current weak assurance is:

1. durably retained with the exact check result and immutable run context;
2. projected into bounded human/JSON inspection and WorkReport citation
   metadata;
3. preserved without upgrade on replay;
4. evaluated by a narrow minimum-assurance gate where a workflow explicitly
   requires stronger evidence; and
5. independently attacked with alternate-executable, malicious-success,
   report-edit, anchor-edit, legacy, restart, replay, and privacy cases.

Do not add arbitrary command execution, executable discovery, a broad policy
DSL, signing, an external witness, or a generic trust service in these slices.

## 4. Benchmark Claim Contract

The measured 49.93% gross-token reduction is credible small-sample evidence and
a weak moat by itself. Both benchmark arms received Workflow OS evidence and
all nine decisions were correct. The lookup arm had more cache hits and fewer
uncached tokens, so the current record does not establish a fixed billed-cost
or universal savings claim.

The stronger product claim to evaluate is:

> The same governed record a reviewer uses to inspect a run can supply a
> replacement executor with what was authorized, denied, completed, and lawful
> next without reconstructing authority from conversation history.

The later LangGraph and Sentence Governors comparison must therefore measure:

- authority and decision correctness after interruption or compaction;
- stale-intent and false-authority use;
- duplicate SideEffects;
- recovery turns and end-to-end task completion;
- gross, cached, uncached, and billed tokens when authoritative;
- latency and operator interventions; and
- which facts are framework-native versus evaluator-authored harness logic.

Workflow OS must not receive credit merely because an evaluator manually
injects its record more consistently. Automatic, versioned checkpoint supply
across integrations is itself the product surface that must be implemented and
tested. Comparative execution remains non-blocking product evidence and cannot
substitute for the assurance and release gates in this plan.

## 5. Governed Delivery Sequence

Execute one reviewed phase at a time:

1. **Product-contract truth correction.** Update current product, hosted,
   integration, and roadmap claims to distinguish accepted path-specific gates
   from unavailable production/generalized behavior. Mark replay enforcement as
   absorbed by Gate 2.
2. **Validator-assurance durable projection.** Persist and expose the existing
   weak assurance without inventing stronger trust.
3. **Minimum-assurance enforcement.** Add one narrow fail-closed consumer for a
   declared stronger requirement; do not introduce a broad policy language.
4. **Independent adversarial review.** Rerun continuity, executable
   substitution, report/anchor mutation, legacy, replay, restart, and privacy
   scenarios from a clean exact-main checkout.
5. **Release re-candidate.** Freeze the accepted commit and regenerate symmetric
   final candidates and evidence from that exact source.
6. **Separate publication decision.** Tag, release assets, packages, and
   announcement remain independently authorized actions.
7. **Comparative recovery evaluation.** Run only after the truth and assurance
   boundaries above are stable. Treat it as product evidence, not release-gate
   substitution.

Provider-write broadening, nested harness execution, enterprise administration,
and v1 claims remain outside this sequence.

## 6. Acceptance

Reconciliation is complete only when:

- current product, hosted, integration, roadmap, and release documents agree on
  which continuity properties are enforced on which paths;
- no accepted gate remains listed as wholly unimplemented;
- no private Core model is presented as a production runtime capability;
- the duplicate replay lane is retired with traceable Gate 2 evidence;
- current validator assurance persists and projects without upgrade;
- stronger declared assurance fails closed when unavailable;
- independent adversarial review accepts the exact release source;
- release candidates, checksums, manifests, and release state bind the same
  exact commit; and
- benchmark language remains bounded to measured conditions and separates
  authority-preservation value from efficiency claims.
