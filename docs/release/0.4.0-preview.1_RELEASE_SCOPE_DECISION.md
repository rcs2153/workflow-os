# 0.4.0-preview.1 Release Scope Decision

Status: adopted for release preparation; candidate admission and publication
remain blocked pending the evidence below. This is not a v1 decision.

Decision date: 2026-11-19. The user explicitly approved separating the bounded
local developer preview from advanced cross-harness admission. This decision
changes delivery sequencing and claims, not runtime enforcement or existing
test results. Earlier publication decisions remain historical and are not
rewritten into acceptance of a new candidate.

## Identity And Promise

Keep the numerical version **`0.4.0-preview.1`**. Use the descriptive title
**Workflow OS 0.4.0-preview.1 - Continuity of Authority Developer Preview**.
Do not move or replace any published tag, release or asset. No beta, stable,
production, enterprise-control-plane or v1 label is admitted.

The release promise is a bounded local experience:

> Introduce Workflow OS into an existing repository, preserve existing agent
> guidance, validate a conservative governance envelope, perform one real
> governed local validation/report operation, and inspect durable evidence,
> approval boundaries and safe replay without provider credentials.

Target users are maintainers and technically sophisticated evaluators. The
goal remains the original ten-minute first-user loop, not a general agent
runtime. The kernel governs supported paths; it does not intercept every tool
an agent can invoke outside those paths.

## In Scope

- Native CLI archives for macOS arm64 and Linux x86-64 musl only, with exact
  source identity, manifests, checksums and bounded user-selected installation.
- Existing-repository dry-run/scaffold, unmanaged `AGENTS.md` preservation,
  project validation and allowlisted metadata-based `first-run` analysis.
- The real `first-run --write-report-artifact --run-id <id>` operation,
  authoritative project-validation citation, truthful report persistence and
  exact replay. Analysis is not an executed repository test or build.
- Supported local filesystem and SQLite run/event/report paths, explicit
  approval and denial, immutable inputs, current-fact checks, interruption
  recovery and bounded `status`, `inspect` and `next-action`. The documented
  filesystem-to-SQLite migration must be tested; no automatic migration or
  stable persisted-state compatibility promise is added.
- Explicit local workflow/handler boundaries: missing handlers fail closed;
  mocks are demonstrations, never execution evidence. Recommendation and
  authoring commands remain bounded local preview tools, not automatic agents.

## Separate Experimental Paths

The following are not acceptance claims of this release: PostgreSQL shared
operation, hosted workers, protected VM deployment, OpenShell execution,
live provider writes, enterprise identity/administration, unattended scheduling
and packaged authenticated cross-harness consequential execution. Existing
fixtures, SDK integrations and proof paths may remain available with explicit
experimental disclosures; this decision enables none of them by default.

Their gates remain mandatory for their own use and claims. The pending offline
VM review is still pending: this release decision is not independent review,
host qualification or permission to boot. The finite cross-harness proof and
[v1 criteria](V1_READINESS_CRITERIA.md) remain unchanged and queued separately.

## Blocker Applicability

### Engineering Tests And Release Assurance

- **Engineering evidence:** The maintainer can run isolated tests on this
  device or provision a disposable VM or managed runner without waiting for
  an outside reviewer. Use the frozen artifact bytes for candidate tests and
  record their hashes, the guest OS and architecture, whether execution was
  native or emulated, the operator, test results, and untested cases. Same-device
  isolation is useful but does not establish independent custody. An ARM guest
  or x86 emulation does not count as native x86-64 execution.
- **Role-separated assurance:** For this preview, a reviewer other than the
  implementer/operator may assess the exact artifacts and inspect the resulting
  evidence without provisioning another machine or repeating every test.
  Record what the reviewer ran versus what they inspected, and disclose any
  shared host, account or toolchain. Do not describe agent review as external
  human assurance. Any expressly required independent reproduction still has
  to be performed.
- **Human usability and admission:** Record actual first-use human steps and
  elapsed time separately from automated runtime. Neither test output nor an
  assurance report admits the release. Missing evidence blocks its named
  claim or decision, not otherwise-authorized engineering work.

These rules do not authorize activation of the protected host, live provider
effects, publication, or a broader readiness claim.

## Finite Delivery Sequence

1. Review this scope and the outstanding-finding inventory. Confirm the local
   contract, default behavior and experimental disclosures; fix only named
   release blockers. Do not add primitive families or mutation capabilities.
2. Freeze a clean merged release commit after those corrections and claim
   changes. Do not silently select moving `main` or reuse older CI as proof of
   the frozen source.
3. Under a separate exact-source dispatch decision, produce both native
   candidates through the existing guarded helper and one persistent claim
   directory. Reconcile ambiguous responses rather than resending. Preserve
   earlier artifacts and records; do not relabel them as the new source.
4. Collect exact-pair clean-room installation evidence on both platforms and
   obtain role-separated review of that evidence. Exercise the [golden path](../implementation-plans/hacker-news-launch-admission-plan.md#4-golden-path)
   in unrelated repositories, report/replay, approval/denial, local restart
   recovery, documented migration, uninstall/state preservation and current
   security audit. Record attempts, human steps, elapsed time and limits.
5. Make a new candidate-admission decision. Only after admission may a separate
   execution phase authorize the exact tag, prerelease, each asset and checksum
   upload. No Rust/npm/Python registry publication is included by default.
6. Make the quiet preview available to a small external maintainer cohort;
   collect first-use feedback before any separately approved Hacker News post.
   Then return to the unchanged finite cross-harness proof and scoped v1 gate.
