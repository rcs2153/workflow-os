# Proportional-Governance Selected Local Project Consumer Plan Review

## 1. Executive Verdict

Plan accepted; proceed to the Core-owned selected-profile fact-source bridge
and test-only equivalence matrix only.

## 2. Scope Verification

The plan stays within planning scope. It does not implement runtime behavior,
change executor or CLI defaults, add automatic approval or persistence, accept
caller-authored authority, invoke providers or OpenShell, execute SideEffects,
add external writes, expose schemas, update examples, add hosted behavior, or
change release posture.

## 3. Selected Consumer Assessment

The existing project-declared authoritative local project-validation path is
the correct first consumer. It has explicit activation and the strongest
available closed chain from immutable declarations through actual local-check
results, approval proof, report generation, and local artifact persistence.
Selecting a generic executor path would force callers to supply authority and
would overstate current product enforcement.

## 4. Source Ownership Assessment

Core ownership of the fixed source registration and fact derivation is
required. Authority cannot come from CLI flags, serialized snapshots, report
citations, persisted receipts, or natural-language summaries. The plan
correctly derives check posture from the actual same-call result and preserves
unknown facts conservatively.

## 5. Ordering Assessment

The plan preserves the accepted ordering: immutable context and complete
preflight precede process use; same-call checks precede assessment; assessment
binding precedes run events; approval presentation proof precedes decision-time
source access; fresh reassessment precedes grant mutation; and receipt
persistence and integrity gates precede artifact persistence.

Denial remains source-free after proof, while post-decision failures retain
truthful workflow and approval state.

## 6. Compatibility Assessment

The three-stage migration is appropriately conservative without becoming a
documentation loop. The next phase writes code, but only for the source bridge
and equivalence matrix. The existing product path remains authoritative until a
separate review proves an additive selected-consumer API is equivalent. CLI
adoption is not bundled into the bridge phase.

## 7. Privacy And Error Assessment

The plan requires stable Core-owned errors and excludes source identities,
snapshots, fact values, bundle commitments, paths, command output, report text,
environment values, and credentials from public Debug and errors. No raw check
or provider payload becomes governance evidence.

## 8. Test-Plan Assessment

The planned matrix covers source substitution, check ownership, preflight
ordering, definition invalidation, approval proof, fresh reassessment, denial,
receipt/artifact composition, partial failure, retry, compatibility, and
non-leakage. Tests must compare behavior, durable state, and event ordering, not
only constructed values.

## 9. Blockers

None for the bridge implementation.

Implementation would be blocked if it exposed a caller-configurable source as
project authority, ran a process before complete preflight, detached the
authoritative check fact from its assessment, changed CLI behavior in the
bridge phase, or removed the existing path before equivalence was proven.

## 10. Non-Blocking Follow-Ups

- Decide bounded snapshot disclosure only after the selected consumer exists.
- Keep multi-step authoritative-governance expansion separately scoped.
- Preserve the existing closed API until later CLI adoption has its own
  compatibility review.

## 11. Recommended Next Phase

Implement the Core-owned selected-profile fact-source bridge and test-only
equivalence matrix. Do not add the selected-consumer API or CLI migration in
the same phase.

## 12. Validation Reviewed

Documentation and diff checks are required before governed phase close.
