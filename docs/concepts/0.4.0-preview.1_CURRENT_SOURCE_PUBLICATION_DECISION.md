# 0.4.0-preview.1 Current-Source Publication Decision

Status: **publication denied; bounded candidate hardening required**

## Decision

Workflow OS must not publish, tag, upload, or announce the current
`0.4.0-preview.1` candidate pair.

Independent assurance accepted the pair for its assurance gate and found no P0
or P1 defect. The separate publication decision applies a stricter irreversible
release boundary. The reproduced dangling-destination-symlink behavior permits
the installer to create the binary outside the selected installation directory
without `--force`. That conflicts with the documented install contract and is
a publication blocker.

The Linux candidate-evidence record also omits the binary hash and binary shape
carried by the macOS evidence record. Those facts exist elsewhere and were
independently recomputed, so the omission is not a runtime-security blocker by
itself. It is nevertheless required hardening for the next pair: native
candidate evidence must be symmetric and self-describing at the bounded
evidence surface used for release admission.

This decision keeps `publication_authorized` false. It authorizes only a
separate bounded hardening lane. It does not authorize any external release
mutation.

## Finding Classification

### Blocking: installer destination symlink handling

The generated installer uses a regular existence check for the destination.
A dangling symlink therefore appears absent, and the later copy follows the
symlink. The installer can create its binary at the symlink target outside the
operator-selected installation directory without explicit overwrite
authorization.

This is blocking because:

- it contradicts the documented bounded install destination;
- it changes where a release artifact writes on the host;
- the behavior occurs on the ordinary installation path;
- `--force` is not required for the redirected write; and
- publication would distribute the known boundary violation irreversibly.

The hardening lane must reject every destination symlink, including dangling
symlinks, before copying. It must preserve ordinary install, explicit forced
replacement of a regular file, overwrite refusal without `--force`, uninstall,
and local-state preservation. Destination creation should use a bounded atomic
strategy rather than relying on a check-then-copy sequence that follows links.

### Required with the next pair: symmetric Linux candidate evidence

The Linux `candidate-evidence.json` contains the archive digest but not
`binary_sha256` or `binary_shape`. The package manifest, release-state record,
hosted workflow evidence, and independent extraction contain those facts.
Therefore the current pair is still attributable and inspectable.

The next candidate workflow must write the same required binary hash and shape
fields for both native targets. Focused tests must reject an evidence record
that omits either field. The release-state validator must continue binding both
records to one exact source commit and must not reconstruct missing candidate
evidence from a different document.

## Required Next Lane

The next bounded implementation lane is:

1. reject regular and dangling destination symlinks in the generated installer;
2. use a bounded destination-creation strategy that cannot follow a destination
   symlink between admission and write;
3. add focused positive and negative installer lifecycle tests;
4. emit and validate symmetric binary hash and shape fields for macOS and Linux
   candidate evidence;
5. run focused maintainer/security review and terminal-green exact-head CI;
6. freeze the resulting merge commit as a new exact source;
7. rebuild both native candidates exactly once from that source; and
8. return through independent evidence inspection and a new governed
   publication decision.

Any source or workflow change invalidates the current native pair for
publication. Existing artifacts remain historical evidence and must not be
rewritten or relabeled as products of the hardened source.
