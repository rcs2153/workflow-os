# First-Run Quiet-Success Artifact Queue Selection Report

## 1. Executive Summary

The next executable lane is one planning and focused-review phase for an
authoritative quiet-success variant of the explicit first-run governed
`WorkReport` artifact path.

The accepted artifact path proves immutable analysis identity, authoritative
project validation, proof-backed approval, truthful report composition,
create-only persistence, exact replay, and bounded recovery. It also requires
two human approval decisions for a command whose only mutation is an explicitly
requested local report artifact. Current product feedback consistently asks
Workflow OS to preserve its evidence and audit posture while reducing
unnecessary interruption for low-risk work.

The selected lane must not reinterpret an approval-required contract as quiet,
auto-approve a gate, or let a caller choose its governance route. It should
plan a distinct exact contract that may complete quietly only when current
authoritative facts cause Core to derive `Proceed` and no explicit minimum
requires approval.

This is queue selection only. Runtime implementation is not authorized before
the plan passes focused maintainer/security review.

## 2. Decision

Selected next phase:

**Plan and review one authoritative first-run quiet-success artifact
composition.**

The plan must define how an explicit local artifact request enters a separately
identified, versioned, exact-contract path; how Core derives its execution and
disclosure decisions from complete current facts; and how any incomplete,
stale, elevated, or approval-required posture fails closed before execution or
artifact persistence.

## 3. Why This Phase Is Next

Current accepted evidence establishes:

- a useful bounded first-run repository analysis;
- a real explicit governed first-run `WorkReport` artifact path;
- immutable run and resolved-context identity;
- authoritative project-validation execution and citation;
- independent execution-disposition and disclosure axes;
- Core-owned workload assessment and runtime reassessment;
- quiet, visible, approval-required, and denied routing foundations;
- approval-presentation proof and proof-marker artifact enforcement;
- create-only local report persistence, replay, and recovery; and
- consistent user feedback that the next product problem is reducing ceremony
  for low-risk work without weakening the ledger.

The remaining gap is composition. The current artifact path truthfully honors
its generated approval policy, but the result is more interruptive than the
bounded local operation appears to require. Workflow OS should demonstrate its
proportional-governance thesis on its strongest onboarding path before adding a
new provider mutation, broader execution profile, UI, or model family.

Explicit command invocation is necessary but insufficient. It communicates
operator intent to request a local artifact. It is not a policy decision,
approval grant, capability, evidence result, or authority receipt.

## 4. Required Entry Conditions

Planning begins from these fixed facts:

1. Ordinary `workflow-os first-run` remains non-mutating.
2. The existing `local/first-run-governance` approval/audit demo remains an
   approval-gated contract and may not be silently reinterpreted.
3. The accepted first-run artifact implementation remains the source of truth
   for immutable analysis identity, trusted handler admission, check citation,
   report construction, persistence, replay, and recovery.
4. Core, not the caller or agent, selects execution disposition and disclosure
   from validated current facts.
5. A declared approval requirement or steward minimum cannot be weakened by
   inference, command flags, explicit invocation, or a local-only target.
6. Local artifact persistence is a real disclosed filesystem mutation even
   though it is not an external provider SideEffect.
7. Quiet success still requires complete evidence, audit, check, limitation,
   risk, and report posture.

## 5. Required Plan Boundary

The plan must define:

- whether the low-ceremony path uses a separate generated workflow and policy,
  a versioned built-in contract, or another explicit declaration source;
- exact compatibility behavior for already scaffolded repositories;
- the complete authoritative input set needed to derive `Proceed`;
- the distinction between explicit invocation intent and approval authority;
- how governance profile, workflow, policy, authority, evidence/check,
  sensitivity, SideEffect, and future steward minima compose monotonically;
- how the local create-only write is classified and disclosed;
- when disclosure may remain quiet and when visible disclosure is mandatory;
- pre-execution and decision-time reassessment, including drift and stale-fact
  rejection;
- report and artifact gates when no approval-proof marker is required by the
  selected exact contract;
- deterministic escalation to approval or denial without hidden auto-approval;
- exact replay, missing-artifact recovery, and crash behavior;
- concise human and bounded JSON output for quiet, visible, approval-required,
  denied, replayed, and recovered outcomes; and
- focused disposable-repository acceptance tests.

The plan must prefer reuse of the accepted first-run artifact, proportional-
governance, current-fact, report, and persistence boundaries. It must not create
a parallel policy engine or a second caller-authored classifier.

## 6. Required Exit Criteria

The plan and focused review are complete only when they establish that:

1. no artifact or runtime state is created without explicit opt-in;
2. the caller cannot select `Proceed`, `Quiet`, approval, or denial;
3. an explicit approval minimum always produces an actionable approval gate;
4. incomplete or unknown safety-relevant facts cannot produce quiet success;
5. current authoritative checks and context are reassessed before execution;
6. drift or runtime escalation can only preserve or strengthen governance;
7. quiet and visible proceed routes retain the same required evidence, audit,
   report, and artifact truth;
8. local artifact persistence remains create-only, bounded, and disclosed;
9. no approval event, presentation proof, or authority receipt is fabricated
   for a route that did not require approval;
10. replay and recovery do not rerun completed work or weaken governance;
11. the existing approval/audit demo and ordinary first-run command remain
   compatible; and
12. no repository command, provider, network call, credential, or external
   SideEffect is introduced.

Implementation must not begin if the plan cannot identify a truthful,
versioned declaration source that distinguishes the low-ceremony contract from
the existing approval-required contract.

## 7. Alternatives Not Selected

### Silently remove the current approvals

Rejected. The current contract explicitly requires approval. Ignoring that
declaration would repeat the policy-enforcement mismatch Workflow OS was built
to prevent.

### Treat command invocation as approval

Rejected. Invocation expresses intent but does not prove policy, authority,
evidence, checks, sensitivity, SideEffect posture, or steward minima.

### Caller-selected `--quiet` or `--no-approval`

Rejected. Presentation preference may affect rendering, but it cannot select
or downgrade governance.

### Broader proportional-governance profiles

Deferred. One exact first-run composition provides a safer product proof than
opening arbitrary profile or command configuration.

### Another provider mutation or OpenShell integration

Rejected as the next phase. Neither reduces the immediate onboarding ceremony,
and OpenShell remains blocked on selected-provider execution and reconciliation
evidence.

### UI or notification delivery

Deferred. Disclosure delivery matters, but a UI is not required to prove the
Core-owned execution-disposition boundary. Quiet decisions may still be shown
by an operator surface without becoming a different governance mode.

### Continue the private continuity or trusted-host lane

Deferred. That lane has substantial accepted private proof. The immediate
product gap is making an already safe public onboarding composition reflect
the project's proportional-governance promise.

## 8. Strict Non-Goals

This selection does not authorize:

- implementation before plan review;
- caller-selected governance routes;
- automatic approval or model self-approval;
- bypass of explicit workflow, policy, profile, authority, evidence/check,
  sensitivity, SideEffect, or steward requirements;
- changing ordinary `workflow-os first-run` into a mutating command;
- weakening or removing the existing approval/audit demo;
- arbitrary repository command or source execution;
- provider reads or writes, network access, credentials, or OpenShell;
- new SideEffect or capability families;
- hosted administration, enterprise identity, or remote policy sync;
- schema or SDK changes by implication;
- recursive agents, agent swarms, or autonomy-level expansion; or
- release-posture changes.
