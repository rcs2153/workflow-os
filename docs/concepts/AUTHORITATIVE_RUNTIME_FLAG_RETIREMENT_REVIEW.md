# Authoritative Runtime Flag Retirement Review

## 1. Executive Verdict

Phase accepted, subject to canonical GitHub CI.

The remaining caller-classified authority shortcut is removed without
broadening the runtime or changing ordinary workflow semantics.

## 2. Scope Verification

The phase stayed within runtime flag retirement. It did not add automatic
approval, inferred authority, RBAC, enterprise identity, capability grants,
OpenShell, sandbox execution, providers, SideEffects, writes, schemas, hosted
behavior, or release changes.

## 3. Authority Assessment

The validated project declaration is now the sole fresh-run activation source
for the closed authoritative preview. Approval resume derives its route from
the immutable activation bound at run creation.

Neither command can assert authority through a runtime switch. Approval
continues to authorize a bounded action; it does not create authority.

## 4. Failure Assessment

Both retired runtime flag forms fail in parsing with stable code
`cli.authoritative_governance.runtime_flag_retired`. Rejection precedes state
backend construction for the operation, run creation, approval mutation,
checks, events, reports, and artifacts.

The bounded error explains that the option remains only on the scaffold
command and does not echo IDs or arbitrary input.

## 5. Compatibility Assessment

Ordinary undeclared execution is unchanged. Project-declared execution is
invoked without a flag. Scaffold opt-in remains supported.

Retiring an experimental compatibility option is justified because retaining
caller-classified authority would contradict the current-authority and
immutable-activation architecture. Current docs include migration guidance.

## 6. Test Quality Assessment

Tests cover quiet, verbose, visible, approval-required, denied, JSON, report
artifact, retry, immutable resume, missing-check, and rejection behavior.
Rejection coverage verifies that no state directory is created.

Existing scaffold tests continue to distinguish declaration authoring from
runtime authority.

## 7. Documentation Assessment

Current run, approve, product-contract, roadmap, plan, report, and review
documents describe the new boundary. Historical phase records remain
unchanged.

## 8. Blockers

None, subject to passing canonical CI.

## 9. Non-Blocking Follow-Ups

- Treat OpenShell as a possible optional execution substrate only after an
  execution-provider contract exists.
- Preserve quiet-success work as risk-proportional rendering and enforcement,

## 10. Recommended Next Phase

capability projection plan. Do not broaden provider mutations first.
