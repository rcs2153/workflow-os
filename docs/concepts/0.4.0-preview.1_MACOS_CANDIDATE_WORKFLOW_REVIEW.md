# 0.4.0-preview.1 macOS Candidate Workflow Review

Status: accepted after blocker correction

## Scope

This owner-conducted maintainer and release-security review evaluates the
native macOS candidate workflow, symmetric candidate-workflow contract tests,
implementation report, and roadmap boundary. It is not independent external
security assurance and does not authorize workflow dispatch, candidate
production, artifact upload, tag or release mutation, registry publication, or
announcement.

## Finding

The first implementation admitted the native runner and target, executed the
packaged binary, and recorded its `file` output, but it did not explicitly fail
if that output was not an arm64 Mach-O executable. It also relied on the
packager to imply the exact archive filename without asserting it in the hosted
workflow.

That was a release-admission blocker. Evidence fields are not enforcement, and
the transfer plan requires exact artifact identity rather than a glob-selected
archive.

## Correction

The workflow now:

- requires the archive name to equal
  `workflow-os-v${version}-${TARGET}.tar.gz`;
- requires `file` output to contain `Mach-O 64-bit executable arm64` before
  writing evidence; and
- has focused regression assertions for both checks.

## Security Review

The corrected workflow:

- is manual-only and has `contents: read` permission;
- rejects inexact source input and requires source/workflow-definition equality;
- checks out exact source without persisting authentication;
- rejects dirty source and non-arm64 hosts;
- pins all external actions and toolchain versions;
- builds and executes the native target;
- uses explicit final-candidate posture;
- verifies exact archive identity, v1 manifest, source, target, version,
  cleanliness, checksum, binary shape, install, overwrite refusal, uninstall,
  and state preservation;
- emits payload-minimal evidence with publication denied; and
- uploads only the archive, checksum, and evidence record for seven days with
  overwrite disabled.

There is no release, tag, registry, branch, pull-request, signing,
notarization, or announcement operation.

## Validation

- `npm run test:candidate-workflow`: five tests passed;
- workflow YAML syntax parse: passed;
- pinned Node 20 `npm run check`: passed;
- pinned Node 20 `npm run check:integrations`: passed;
- `npm audit --audit-level=moderate`: zero vulnerabilities after the exact
  network-enabled retry of a sandbox DNS refusal;
- `npm run check:docs`: passed; and
- `git diff --check`: passed.

## Residual Boundary

No hosted run has exercised the workflow. Runner assignment, native execution,
candidate bytes, workflow artifact identity, expiry, download verification,
and exact cross-target source equality remain future release-phase evidence.
The current GitHub connector does not consume a Workflow OS external-action
capability, so later dispatch remains disclosed out-of-kernel work under a
separate proof-backed gate.

## Verdict

Accepted with no remaining P0 or P1 blocker in this implementation boundary.
Merge still requires terminal-green exact-head CI. After merge, that exact
commit may become candidate source only through a separate governed release
phase that enumerates both native workflow dispatches and artifact reads.
