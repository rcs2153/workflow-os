# Authoritative Governance Scaffold Opt-In Review

## 1. Executive Verdict

**Phase accepted with blocker fixed; proceed to external-repository opt-in
evaluation.**

The phase adds a narrow, truthful setup path for behavior that was already
implemented and accepted. It does not create a second governance classifier,
new execution authority, or a silent default. One setup-integrity blocker was
found during review and fixed before acceptance: unknown scaffold options were
previously ignored, so a misspelled opt-in could appear to succeed without
enabling authoritative execution.

## 2. Scope Verification

The implementation stayed within the approved scaffold boundary:

- one `init-repo-governance` flag was added;
- only the existing closed project declaration is generated;
- no declaration is generated by default;
- scaffolding executes no workflow or local check;
- dry-run remains non-writing;
- existing file preservation and `--force` behavior remain unchanged; and
- later execution continues through the existing authoritative path.

No new policy semantics, local-check profiles, provider paths, OpenShell
integration, SideEffect execution, external writes, hosted behavior, workflow
generation, or release changes were introduced.

## 3. CLI And Compatibility Assessment

The option name matches the existing compatibility preview:

```text
--authoritative-governance
```

The generated declaration exactly matches the supported project contract:

```yaml
governance:
  authoritative_execution:
    profile: observe_and_report
    local_check_profile: workflow_os_project_validation
```

Default scaffold content remains unchanged, and default output gains no new
posture line. Explicit normal and dry-run invocations disclose the selected
profile and local-check profile. This is appropriately additive.

## 4. Runtime Truth Assessment

The implementation does not claim that scaffolding itself performs validation
or creates a WorkReport. Documentation distinguishes the non-executing
scaffold from the effect of the generated declaration on later runs:

- Core derives the route;
- the fixed project-validation check is used;
- approval/resume integrity remains enforced;
- eligible terminal runs use the accepted WorkReport artifact path; and
- no arbitrary command, provider, network, credential, or external-write
  authority is added.

That boundary is accurate and avoids presenting a configuration convenience as
a new runtime capability.

## 5. Failure And Privacy Assessment

Existing scaffold file conflicts still fail before partial writes. Existing
agent guidance remains preserved unless the user explicitly selects `--force`.
Output contains only fixed posture labels and does not copy manifest, file, or
repository payloads.

The review blocker was:

```text
init-repo-governance accepted unknown options and silently ignored them
```

This was unacceptable for a security-relevant opt-in because a misspelled flag
could leave the project undeclared. The parser now validates the complete
option set before scaffold planning or writing. A regression proves the
misspelled option fails with no manifest, workflow directory, or runtime state.

## 6. Test Quality Assessment

Focused tests cover:

The tests exercise the public CLI and filesystem outcomes rather than only
constructing internal values.

## 7. Documentation Assessment

The CLI guide, current product contract, agent harness quickstart, onboarding
plan, profile activation plan, roadmap, implementation plan, and phase report
all state:

- the option is explicit;
- the default remains unchanged;
- the selected profile is closed;
- scaffolding is non-executing;
- later authoritative runs may execute the fixed check and persist a report

- providers, OpenShell, SideEffects, and external writes remain unsupported by
  this phase.
