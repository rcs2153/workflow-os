# Core-Owned Authoritative Runtime-Fact Derivation Review

## 1. Executive Verdict

Phase accepted; proceed to authoritative scaffold default activation.

## 2. Scope Verification

The implementation stayed within the closed one-step runtime-composition scope.
It did not add multi-step authority, default activation, inferred commands,
automatic approvals, providers, OpenShell, SideEffect execution, writes,
hosted behavior, schemas, examples, or release changes.

## 3. Fact Ownership Assessment

The new closed request has no runtime-fact field. Core constructs the only
neutral fact after immutable shape preflight. Authority, check posture, static
minima, sensitivity, action class, and side-effect posture come from their
existing canonical sources.

The CLI no longer constructs facts for selected or non-selected steps.

## 4. Shape And Immutability Assessment

The closed route resolves one immutable workflow record, requires exactly one
step, and requires that step to match the selected step. Multi-step input fails
before local-check process use, run events, or bundle persistence.

Approval reassessment validates the same stored immutable shape before executing
the decision-time check or applying an approval decision.

## 5. Route And Disclosure Assessment

Core alone selects quiet, visible, approval-required, or denied behavior.
Fresh CLI execution supplies a bounded visible-delivery capability without
predicting the route.

Only visible proceed invokes delivery. Quiet and approval-required regression
tests prove zero handler calls. Existing denied CLI coverage proves no visible
delivery output.

## 6. Check And Approval Assessment

The selected evidence/check posture comes from the accepted same-call result.
A failed check cannot become quiet or visible success.

Aggregate approval reassessment executes the same closed profile again,
compares the resulting binding with the durable assessment, validates
presentation proof, and only then applies the decision. Authored step approval
remains separate.

## 7. Compatibility Assessment

Existing explicit-fact APIs and their tests remain intact for lower-level
embedding and test use. The closed CLI path uses only the fact-free API.

## 8. Privacy And Error Assessment

New errors are stable and bounded. Debug output does not expose execution
inputs, runtime facts, selected identifiers, check output, paths, credentials,
or disclosure content.

## 9. Test Quality Assessment

The focused tests exercise the primary trust boundaries rather than only
constructor shape:

- Core-owned quiet route and non-consumption of visible capability;
- Core-owned aggregate approval and decision-time reassessment;
- multi-step pre-state rejection;
- failed check rejection;
- all existing CLI route outcomes; and
- lower-level API compatibility through the broader suite.

No blocker remains.

## 10. User-Feedback Alignment

Recent external evaluation describes Workflow OS as a coherent and honest
local-first governance kernel whose next challenge is reducing ceremony without
losing evidence. This phase directly supports that direction: callers provide
capabilities, while Core derives and enforces the least-permissive complete
route from canonical facts.

The evaluation's Node-version and duplicate missing-manifest diagnostics are
valid product polish follow-ups, not blockers for this trust-boundary phase.

## 11. Blockers

None.

## 12. Non-Blocking Follow-Ups

- Keep Node 20 as the validated integration-test runtime and improve failures
  under unsupported Node versions.
- Remove the duplicated missing-manifest diagnostic in the pre-scaffold
  validation path.
- Continue quiet-success UX work after default activation.
- Plan multi-step authoritative facts only when each step has real current
  authority, check, and SideEffect sources.

## 13. Recommended Next Phase

Implement authoritative scaffold default activation with an explicit opt-out.
Do not add providers or new mutation behavior in that phase.
