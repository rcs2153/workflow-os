# First-Run Governed WorkReport Artifact Queue Selection Report

## 1. Executive Summary

The next executable lane is one planning and focused-review phase for an
explicit, opt-in first-run governed WorkReport artifact path.

Workflow OS already performs real bounded repository posture analysis through
`workflow-os first-run`, but the generated runnable follow-up remains an
optional mock approval/audit demonstration. The selected lane should connect
the existing safe first-run analysis to the existing WorkReport and local
artifact foundations without pretending that repository commands, providers,
or source-code analysis occurred.

This is a runtime-composition selection, not authorization to implement before
the plan passes focused maintainer/security review.

## 2. Decision

Selected next phase:

**Plan and review one explicit first-run governed WorkReport artifact vertical
slice.**

The plan must preserve ordinary `workflow-os first-run` as non-mutating. It
must define one explicit opt-in command posture that captures the exact same-
call bounded analysis in a validated WorkReport and idempotent local artifact,
then returns bounded artifact metadata and an inspectable next action.

## 3. Why This Phase Is Next

Current accepted evidence establishes:

- safe existing-repository scaffolding that preserves unmanaged agent
  guidance;
- bounded first-run repository metadata inspection and governance posture;
- concise and verbose human output plus machine-readable JSON;
- review-only workflow recommendations and inactive draft authoring;
- proportional-governance routing and quiet-success behavior;
- immutable run and report identity foundations;
- validated WorkReport construction;
- gated, create-only local artifact persistence and exact replay; and
- default authoritative governance for newly scaffolded repositories.

The remaining user-visible gap is composition. First-run already produces the
useful analysis, but it deliberately creates no run, artifact, evidence, or
durable report. The generated `local/first-run-governance` workflow still uses
a mockable placeholder and proves approval/event mechanics rather than real
repository posture work.

Selecting another model family would widen the docs/runtime gap. Selecting a
provider mutation, OpenShell path, or arbitrary local command would either
cross an existing blocker or add risk unrelated to the immediate onboarding
value.

## 4. Required Entry Conditions

Planning begins from these fixed facts:

1. Ordinary `workflow-os first-run` remains real, bounded, and non-mutating.
2. Safe metadata inspection may not expand into arbitrary source-file reads.
3. The current analysis must not be recomputed from a different repository
   snapshot after approval or artifact identity is established.
4. Mock skill success is not execution evidence and cannot be cited as such.
5. Local artifact persistence is itself a disclosed local side effect.
6. Existing WorkReport, artifact-integrity, approval-proof, and exact-replay
   gates should be reused rather than reimplemented.
7. Report creation must not imply that skipped checks, unavailable evidence,
   deferred provider work, or unsupported SideEffects completed.

## 5. Required Plan Boundary

The plan must define:

- an explicit opt-in CLI posture, with ordinary first-run behavior unchanged;
- one canonical same-call first-run analysis record and content commitment;
- exact repository, project, manifest, metadata, recommendation, and
  governance-posture identity sufficient to reject drift;
- run and artifact identity, idempotency, conflict, interruption, and replay
  semantics;
- proportional-governance and approval behavior without creating a second
  fake approval layer;
- truthful WorkReport sections for evidence, checks, side effects, incomplete
  work, limitations, risk, and handoff;
- local artifact-write disclosure and no external side-effect claim;
- bounded human and JSON output that returns references and metadata rather
  than the complete report body by default;
- the relationship to the optional mock approval/audit demo, including whether
  that demo remains unchanged or gains a later deprecation path; and
- disposable existing-repository acceptance tests.

## 6. Required Exit Criteria

The planning/review phase is complete only when focused maintainer/security
review accepts a design that proves:

1. no state or artifact is created without explicit opt-in;
2. the report cites the exact same-call first-run analysis, not a later
   reconstruction;
3. repository or manifest drift fails closed before artifact creation;
4. exact replay returns the existing equal artifact without duplicate state;
5. conflicting identity or artifact content fails closed without overwrite;
6. missing evidence and skipped checks remain explicit and cannot become
   success claims;
7. no mock handler result is used as evidence;
8. no repository command, provider, network call, or external write occurs;
9. errors and output remain payload-minimizing and non-leaking; and
10. default onboarding and existing ordinary CLI behavior remain compatible.

Implementation must not begin if the plan cannot establish the immutable
same-call analysis boundary or truthful report identity.

## 7. Alternatives Not Selected

### OpenShell provider wiring

Rejected as the next phase. Stable `v0.1.5` still lacks mandatory selected-
driver execution, observation, reconciliation, and cleanup facts. The posted
upstream comment does not close those blockers.

### Direct native Cargo execution expansion

Rejected. The accepted native observer remains preflight evidence, not
filesystem, network, process, or lifecycle containment. Cargo clippy execution
cannot be authorized by self-observation alone.

### Another provider mutation

Rejected. Existing comment and draft-pull-request proofs do not authorize a
third mutation family or default write behavior.

### Public GitHub read-only adoption

Deferred. The private capability-gated read is accepted, but public adoption
still requires authored operation selection, configuration, credential,
recovery, and disclosure design. It is less immediate than making the existing
first-run value durably inspectable without a provider dependency.

### Another model-only primitive

Rejected. Current report, artifact, governance, immutable-input, and onboarding
models are sufficient to plan the selected composition path.

### UI disclosure work

Deferred. Visible disclosure remains a delivery property, but a UI is not
required to prove the selected local artifact boundary.

## 8. Strict Non-Goals

This selection does not authorize:

- implementation before focused plan review;
- changing ordinary `workflow-os first-run` into a mutating command;
- automatic runs, approvals, artifacts, or workflow promotion;
- arbitrary source inspection or repository command execution;
- local shell, Cargo, npm, test, lint, or build execution;
- provider reads or writes, network access, or credentials;
- OpenShell integration or native sandbox claims;
- new SideEffect families or external mutations;
- hosted storage, multi-tenancy, enterprise identity, or administration;
- recursive agents, agent swarms, or nested harness execution;
- schema or SDK changes by implication; or
- release-posture changes.
