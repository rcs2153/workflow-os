# 0.4.0-preview.1 Candidate Hardening Implementation Report

Status: **implemented; focused review and exact-head CI required**

## Summary

This phase implements the minimum hardening required by the denied
`0.4.0-preview.1` publication decision:

- generated installers reject destination symlinks, including dangling
  symlinks, even when `--force` is supplied;
- installers no longer copy directly through the final destination path;
- destination creation uses an atomic no-follow hard-link boundary;
- focused tests prove that a dangling destination symlink cannot create the
  binary outside the selected installation directory;
- the Linux candidate workflow records `binary_sha256`, `binary_shape`, and
  `native_machine`, matching the macOS evidence surface; and
- workflow contract tests require those fields for both native targets.

No native candidate was produced. No release authority changed.

## Installer Boundary

The generated installer now follows this sequence:

1. parse only the optional `--force` flag;
2. create the selected installation directory;
3. reject the final destination when it is any symlink, including a dangling
   symlink;
4. reject an existing destination when it is not a regular file;
5. reject an existing regular destination unless explicit replacement was
   requested;
6. create a private temporary file inside the selected directory;
7. copy and set executable mode on that private file;
8. for explicit replacement, remove only the admitted regular destination path
   entry;
9. create the final destination with a hard link, which fails atomically if any
   path entry appears concurrently; and
10. remove the temporary name and clear cleanup traps.

The source binary is never copied to the final path. A destination symlink is
therefore neither followed during admission nor during creation. A path that
appears between admission and creation causes hard-link creation to fail
closed. The temporary and final names are on the same selected filesystem, so
the hard-link admission point does not cross a filesystem boundary.

This phase does not reject a symlink used as the installation directory itself.
The selected directory may intentionally be a user-managed link. The fixed
boundary is the final executable path that previously redirected an
unreviewed write.

## Evidence Symmetry

The Linux final-candidate workflow now computes the packaged executable's
SHA-256 and native `file` shape, rejects a shape that is not a static x86-64 ELF
executable, and records:

- `binary_sha256`;
- `binary_shape`; and
- `native_machine`.

The existing release-state record already carries the independently verified
Linux values. This change makes the bounded candidate-evidence record itself
self-describing and symmetric with the macOS record. It does not rewrite the
historical candidate evidence or claim that the old artifact was produced by
the hardened source.
